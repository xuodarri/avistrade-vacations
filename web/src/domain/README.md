# Движок проверки отпусков (`src/domain`)

Чистый TypeScript без зависимостей от Next.js и базы: `server-only` не импортирует, поэтому
его можно звать и из клиентских компонентов (подсветка календаря на лету). Данные (сотрудники,
планы, правила, исключения) приходят из базы через переходник `fromDb.ts` или из демо-набора
`sample.ts`. Тесты — `npm test` (vitest), файлы в `__tests__/`.

```ts
import { checkPlan, createContext, dayLoad, findWindows, groupOf, teamConflicts } from '@/domain';
import { employeeFromDb, planFromDb, rolesFromDb, rulesFromDb, exceptionsFromDb, dbRuleCode } from '@/domain/fromDb';
```

## Подключение к серверу — `src/server/engine.ts`

Серверная обёртка собирает контекст из репозиториев (`src/server/db/repo.ts`) и зовёт движок:

| Функция | Что возвращает |
|---|---|
| `checkPlan(employeeId, parts, year?, { submitting? })` | `PlanCheck`: `verdict` и `findings` с кодами базы (R01…), `partNo`, днями конфликта, `title`, `basis`, `employeeIds`, `dateBound`. Части — сохранённые (`RequestPart`) или с экрана (`PartInput`) |
| `groupLoad(employeeId, year)` | загрузка группы по дням года без имён: `{ busy, limit, full }`, `limit: 0` — лимита нет; льготнику `full` всегда `false` |
| `freeWindows(employeeId, parts, partNo, year?, { strict })` | до 3 свободных окон той же длины для части с номером `partNo`; `strict: true` — только окна, с которыми весь план проходит без запретов |
| `shiftVerdicts(employeeId, parts, partNo, year?)` | для перетаскивания: по каждой дате начала части той же длины в пределах года — `{ status, results }`, где results — запреты, предупреждения и исключения этой части и плана в целом, в сжатом виде (без title и basis, дни конфликта — только у лимита, зависимостей и наложения). Один вызов на старте переноса, ~350 вариантов за 40–60 мс |
| `edgeVerdicts(employeeId, parts, partNo \| null, type, fixed, year?)` | для растягивания края: по каждому дню d года — `{ status, results }` для выделения [min(fixed, d), max(fixed, d)]; `partNo: null` — новая часть. ~365 вариантов за 130–200 мс, ответ ~220 КБ |
| `checkChange(employeeId, partId, { kind, newStart?, newEnd?, reason? }, { requestedOn?, year? })` | заявка на изменение согласованной части (`move` / `shorten` / `cancel`): `PlanCheck` плана с новыми датами + R14 от прежнего начала + R21 «начавшуюся не меняет»; `windows` — окна той же длины, если мешает лимит или зависимость |
| `checkPartChange(changeId)` | то же для сохранённой заявки из `part_changes` (очереди руководителя и HR); у `extend` и `recall` — `null` |
| `sicknessExtension(partId, sickStart, sickEnd)` | продление по больничному (ст. 171): новый конец, сколько дней добавлено, праздники в хвосте |
| `recall(employeeId, partId, returnOn)` | отзыв (ст. 174): использовано / вернётся в остаток, запрет для работника до 18 лет (`allowed: false`, `message`) |
| `normFixes(employeeId, parts, target, year?)` | до 3 советов «что сократить» при переборе нормы для экрана сотрудника: согласованные части не трогаются; ok раньше warn, затем сама target, затем обрезка с конца |
| `substituteCandidates(employeeId, { start, end }, year?)` | коллеги для выбора замещающего: свой отдел, отделение, остальные; свободные раньше; у занятых — `busy` (дни пересечения) |
| `trimSuggestions(employeeId, parts, draftPartNo?, year?)` | где освободить дни при превышении нормы: `TrimAdvice[]` — часть, «было → станет», сколько дней освобождается, статус, задевает ли согласованную часть, предупреждения. Только варианты без запретов |
| `groupAbsences(employeeId, year)` | по всем дням года, кто отсутствует: `{ peers, deputies }` — id коллег по группе лимита и тех, без кого сотрудник не уходит. Без дат чужих отпусков; показывать ли имена, решает вызывающий |
| `teamConflicts(year?)` | `TeamReport` для Ганта HR: коды движка, код базы — `dbRuleCode(code)` |

Контекст сервера учитывает открытые заявки на перенос (`changes.forYear`): у коллег заняты и старые, и новые даты, пока заявка не решена. Год проверки заявки берётся по самой части.

Коды правил базы → движка: R01 `groupLimit`, R02 `roleDependencies`, R03 `summerLength`,
R04 `noticeMonth`, R05 `longPart`, R06 `yearNorm`, R07 `noOverlap`, R08 `holidays`,
R09 `firstVacation`, R10 `maxParts`, R13 `scheduleDeadline`, R14 `rescheduleNotice`, R15 `substitute`, R00 `pastDates`, R16 `unpaid190Limit`, R17 `unpaid189Limit`, R18 `payRequest`, R19 `halfYearDeadline`, R20 `treatmentLeave`, R21 `changeLocked`. R00, R16, R17 и R21 действуют, даже если строк в базе ещё нет.
R11 (напомнить об уведомлении) и R12 (ст. 189 — только даты) отдельными правилами не
проверяются: ст. 189 выводит из-под лимитов сам тип части. В базе `severity` — жёсткость при
сборке графика (её правит HR), `params.stages.adhoc` / `inplan` — на других этапах,
`params.value` — N из названия правила, `params.benefitApplies` — действует ли на льготников.

Даты везде — строки `YYYY-MM-DD`, последний день отпуска включительно.

## Функции для экранов

| Функция | Что возвращает | Кто зовёт |
|---|---|---|
| `createContext({ employees, plans, ...})` | контекст проверки с умолчаниями: сегодня, этап `collect`, роли и правила по умолчанию, статусы «на согласовании» и «согласована» занимают место | все |
| `checkPlan(employee, plan, context)` | `CheckResult`: общий статус `ok / warn / block`, результаты по правилам, дни и статус каждой части, сумма дней и норма | сотрудник, руководитель |
| `groupOf(employee, employees, roles)` | группа: кто делит лимит (`memberIds`), лимит, кто должен быть на месте (`dependencyIds`), подпись | все |
| `dayLoad(group, date, allPlans, { excludeEmployeeId })` | `DayLoad`: сколько отсутствует, лимит, свободно мест, нет ли на месте связанной роли, `full`, праздник. **Без имён** | календарь сотрудника |
| `loadRange(group, from, to, allPlans, opts)` | то же на отрезок дней | календарь сотрудника |
| `findWindows(employee, plan, partId, context, opts)` | до 3 ближайших свободных окон той же длины (в днях отпуска): по умолчанию начало в понедельник, −6…+12 недель, в пределах года плана. `strict: true` — окно проходит весь `checkPlan` без запретов (ищет шире: −120…+240 дней); если запрет не от дат, окон нет | сотрудник, HR («вернуть с датами») |
| `shiftVerdicts(employee, plan, partId, context)` | `Record<дата начала, CheckResult>` — полный checkPlan для каждого допустимого начала части той же длины в пределах года | перетаскивание части |
| `edgeVerdicts(employee, plan, partId \| null, type, fixed, context)` | `Record<d, CheckResult>` — полный checkPlan для выделения [min(fixed, d), max(fixed, d)] на каждый день года; новая часть получает id `EDGE_PART_ID` | растягивание края |
| `trimSuggestions(employee, plan, context, { draftId?, overflow? })` | каждая основная часть, обрезанная с конца или с начала ровно на лишние дни отпуска (праздники не в счёт), с полной проверкой плана; без запретов, по порядку: без предупреждений → не задевает согласованные → меньше сдвиг начала. Часть целиком не убирается | экран сотрудника |
| `groupAbsences(group, from, to, allPlans, opts)` | по дням: `peers` и `deputies` — id отсутствующих коллег по группе лимита и связанных ролей | экраны, где HR разрешил имена |
| `teamConflicts(allEmployees, allPlans, rules, context?)` | `TeamReport`: все запреты, предупреждения и разрешённые исключением нарушения по компании (`conflicts`, у каждого `employeeId` и `resolved`), итог по сотруднику для раскраски Ганта, флаги для HR (`notices`: срок графика) | Гант HR |

Справочные функции календаря: `holidaysOf(year)`, `holidaysBetween`, `isHoliday`, `isWorkingDay`,
`vacationDays(start, end)` (календарные дни минус праздники), `vacationEnd(start, days)`,
`summerDays`, `workingYear(hiredOn, date, shiftDays)`, `radunitsa(year)`. Тексты дат:
`rangeText('2027-06-14', '2027-06-20')` → «14–20 июня», `daysText(21)` → «21 день».
Каждое правило доступно и отдельно: `import { rules } from '@/domain'; rules.groupLimit(...)`.

### Результат правила

```ts
{
  code: 'groupLimit', title: 'Лимит группы одновременно в отпуске',
  status: 'block',                  // ok | info | warn | block | exception | off
  message: 'Часть 1: 14–20 июня мест нет (лимит 2)',
  basis: 'Регламент: лимит одновременно в отпуске; ч. 1 ст. 168 ТК',
  partIds: ['E13-1'], dates: [{ start: '2027-06-14', end: '2027-06-20' }],
  employeeIds: ['E14', 'E15'],      // кто занимает места: экран руководителя и HR может показать имена
  severity: 'block',                // жёсткость нарушения; у exception — какой она была бы
  exception: undefined,             // исключение HR, если оно сняло нарушение
  dateBound: true,                  // сдвиг дат может исправить; false — норма, число частей, часть от 14 дней, перенос, срок графика
}
```

В `checkPlan().results` каждое включённое правило есть хотя бы раз: нарушения — по одной строке
на часть, если нарушений нет — одна строка `ok` (или `off` с причиной). В `message` нет имён
коллег — его можно показывать сотруднику как есть; имена экран берёт по `employeeIds` сам.

## Как выносится вердикт

1. Правило выключено → `off`, «Правило выключено».
2. К части не относится (ст. 189 и социальные отпуска для лимитов, нет переноса и т. п.) → `off` с причиной.
3. Сотрудник — льготник ч. 4 ст. 168 (`benefits`) или моложе 18 (`minor`), а правило с
   `appliesToBeneficiaries: false` → `off`, «Не применяется: льгота ч. 4 ст. 168 ТК (…)».
4. Не нарушено → `ok`, либо `info`, если есть что сказать (праздники, недораспределённые дни).
5. Нарушено → жёсткость `severityByStage[этап] ?? severity`; находка может её только смягчить
   (незаполненный замещающий вне отправки — не строже предупреждения). Этап части: `approved`, если часть
   согласована (уже в утверждённом графике), иначе этап контекста — `collect` или `adhoc`.
6. Для правил регламента (`source: 'regulation'`) при `block` / `warn` ищется исключение HR по
   сотруднику, правилу и части (исключение без `partId` — на весь план) → `exception`,
   «…Разрешено исключением РО1: причина». Нормы закона исключением не снимаются: там, где ТК
   допускает соглашение, отмечается согласие (`part.earlyConsent`).

Общий статус плана: `block`, если есть запрет; `warn`, если есть предупреждение; иначе `ok`.
`exception` и `info` его не портят.

**Последствия для подачи.** У каждого нарушения (`block`, `warn`) есть `consequence`:

- `law` — запрет нормы ТК или ошибка данных (даты в прошлом, перебор нормы, нет части от 14 дней,
  пересечение своих частей, больше 3 месяцев по ст. 190, замещающий — сам сотрудник или не найден).
  Подать нельзя, исключением не снимается;
- `exception` — запрет правила регламента (лимит группы, «без кого не уходит», замещающий в отпуске…).
  Подать можно, план уходит как запрос исключения: решают руководитель и HR;
- `warning` — предупреждение, подаче не мешает.

`CheckResult.summary` — `{ canSubmit, needsException, law, exceptions, warnings }`; на сервере
`PlanCheck.canSubmit`, `needsException`, `reasons: { law, exception }` (тексты). Разрешённое
исключением нарушение (`status: 'exception'`) последствий не имеет.

«Сегодня» для всех проверок — `todayIso()` из `config.ts`; для демо его фиксирует переменная
окружения `DEMO_TODAY=2026-10-26`.

## Правила

| Код | Что проверяет | Параметры | Жёсткость по умолчанию | Льготникам | Основание |
|---|---|---|---|---|---|
| `pastDates` (R00) | не согласованная часть начинается не раньше сегодня + N дней; отпуск задним числом не оформляется | `daysAhead: 1` | запрет (`law`) | да | — |
| `groupLimit` | на каждый день части отсутствующих коллег группы + сам ≤ лимит роли | лимит — в политике роли | запрет; для части из графика — предупреждение | нет | Регламент: лимит; ч. 1 ст. 168 |
| `roleDependencies` | связанные роли на месте все дни части | связи — в политике роли | запрет; из графика — предупреждение | нет | Регламент: кто без кого не уходит; ч. 1 ст. 168 |
| `summerLength` | летних дней (1.06–31.08, без праздников) ≤ N; смежные части без рабочих дней между ними — один отпуск. Пометка риска ч. 1 ст. 174 / ч. 4 ст. 168 | `days: 14` | запрет регламента (`exception`) | нет | Регламент: летний период |
| `noticeMonth` | от подачи (или сегодня) до начала ≥ N дней; у переноса не проверяется (там R14) | `days: 30` | запрет регламента; из графика — не проверяется | да | Регламент: заявление за месяц; ст. 169 |
| `longPart` | есть основная часть ≥ N дней | `days: 14` | запрет | да | ч. 1 ст. 174 |
| `yearNorm` | основных дней ≤ норма + доп. дни; меньше — `info` «не распределено» | — | запрет | да | ст. 155, 158–162 |
| `firstVacation` | основной отпуск не раньше приёма + N месяцев (или согласие / право ч. 2–3 ст. 166) | `months: 6` | предупреждение | да | ч. 1 ст. 166 |
| `noOverlap` | даты частей корректны, части не пересекаются | — | запрет | да | ст. 151, 174 |
| `unpaid190Limit` (R16) | за свой счёт по ст. 190 за год (календарные дни): больше N — предупреждение, больше maxDays — запрет | `days: 30, maxDays: 90` | запрет сверх 3 месяцев | да | ст. 190 |
| `unpaid189Limit` (R17) | обязательный за свой счёт по ст. 189 за год: больше N — предупреждение, сверх — по договорённости (ст. 190) | `days: 14` | предупреждение | да | ст. 189 |
| `rescheduleNotice` (R14) | перенос или отказ по соглашению заявлен ≥ N дней до прежнего начала; законные основания ст. 171 срока не требуют | `days: 14` | запрет регламента (`exception`) | да | Регламент; ч. 1 ст. 171 |
| `changeLocked` (R21) | начавшуюся или прошедшую согласованную часть сотрудник не переносит и не сокращает — это продление или отзыв через HR | — | запрет (`law`) | да | ст. 171, 174 |
| `payRequest` (R18) | не нарушение — у основной части с отметкой «нужны отпускные» пометка риска ст. 175–176 (info), без отметки ничего | — | инфо | да | Регламент |
| `treatmentLeave` (R20) | лимиты и сроки регламента распространяются на за свой счёт (ст. 190) и плановое лечение; выключено — эти виды не проверяются R01, R02, R04. У части лечения — пометка риска (info) | — | инфо | да | Регламент |
| `halfYearDeadline` (R19) | полугодовой график (регламент): часть января–июня — заявление до 15 января, июля–декабря — до 15 июля того же года; вне графика и для согласованных не проверяется. Пометка `legalRisk`: ТК — годовой график до 5 января | `h1Month/h1Day: 1/15, h2Month/h2Day: 7/15` | запрет регламента (`exception`) | да | Регламент |
| `substitute` (R15) | у части указан замещающий (`substituteId`), это не сам сотрудник и не уволенный, и он не в отпуске ни в один день части (его части в любом статусе, кроме отклонённых). Не указан: в черновике и у поданной части — предупреждение («укажите, кто вас замещает» / «замещающий не указан»), при отправке (`context.submitting`) — по жёсткости правила. Дни пересечения — в `dates`, замещающий — в `employeeIds` | — | запрет; из графика — предупреждение | да | регламент: в заявлении указывается коллега, который будет замещать |
| `maxParts` | основных частей ≤ N | `parts: 3` | запрет | да | ч. 1 ст. 174: больше двух — если разрешает ЛПА |
| `holidays` | праздники внутри части — отпуск длиннее (только `info`) | — | инфо | да | ч. 2 ст. 151, ч. 1 ст. 147 |
| `scheduleDeadline` | флаг для HR: ТК — годовой график до 5 января, регламент — полугодовой до 15.01 и 15.07; без коллективного договора это расходится с ТК | `month: 1, day: 5` | инфо | — | ч. 2 ст. 168 |

Вид `treatment` «Плановое лечение» (регламент; юридический риск — по ТК это больничный, ст. 171)
подчиняется лимиту группы, зависимостям ролей и сроку «за месяц», но не входит в норму дней, к нему не
относятся лето и лимиты ст. 189/190. Флаг части `needsPay` «нужны отпускные, не больше оклада» (регламент) —
только данные, проверок нет. Правила регламента, которые расходятся с ТК, несут `legalRisk` — текст
риска; он переходит в каждый `RuleResult` (в базе — `params.legalRisk`).

Ст. 189 (обязательный отпуск без сохранения) и социальные отпуска не подчиняются лимиту,
зависимостям и сроку подачи, но сами занимают место: коллега в отпуске по ст. 189 тоже отсутствует.
Без сохранения (ст. 189, 190) в норму основного отпуска не входит.

### Политики ролей (`DEFAULT_ROLES`)

| Роль | Лимит среди | Лимит | Должны быть на месте |
|---|---|---|---|
| ИД | — | — | ЗАВ и ЗТВ |
| ЗАВ, ЗТВ | — | — | ИД |
| РО | РО под тем же ЗАВ/ЗТВ | 1 | свой ЗАВ/ЗТВ |
| НО | НО отделения | 1 | РО отделения |
| МС | МС отдела | 1 | НО отдела |
| МПП | все МПП компании | 2 | — |
| СП | — | — | — |

Круг задаётся полем `Scope`: `company`, `unit` (отделение), `dept` (отдел), `same-manager`, `own-manager`;
у каждой зависимости свой круг: `dependsOn: [{ role: 'НО', scope: 'dept' }]`. В базе это группы
ограничения (`groups`) и зависимости ролей (`role_dependencies`), `rolesFromDb` собирает из них политики.

## Календарь

Нерабочие праздники — перечень, объявленный нерабочим Указом № 157 от 26.03.1998 (сверено с
[pravo.by](https://pravo.by/gosudarstvo-i-pravo/gosudarstvennye-prazdniki/) 26.10.2026):
1, 2 и 7 января, 8 марта, 1 и 9 мая, Радуница, 3 июля, 7 ноября, 25 декабря. Радуница считается
от православной Пасхи (+9 дней): в 2027 году Пасха 2 мая, Радуница — вторник 11 мая.
Праздник на выходном в Беларуси не переносится.

Переносы 2027 — постановление Совмина от 03.10.2026 № 499 «О переносе рабочего дня в 2027 году»
([etalonline.by](https://etalonline.by/novosti/korotko-o-vazhnom/perenos-rabochikh-dney-2027/)):
понедельник 10 мая — выходной, суббота 8 мая — рабочая. Выходной от переноса праздником не
становится и в отпуск входит; на `isWorkingDay` он влияет. Переносы на другие годы дописываются
в `WORKDAY_TRANSFERS`. Сид базы берёт праздники отсюда (`holidaysOf(2027)`); уже созданная
база обновится после `npm run db:reset`.

## Файлы

- `types.ts` — типы предметной области;
- `dates.ts` — даты и русские тексты дат;
- `calendar.ts` — праздники, переносы, подсчёт дней, лето, рабочий год;
- `config.ts` — правила, роли и настройки по умолчанию, `createContext`;
- `groups.ts` — группы и отсутствия;
- `rules.ts` — правила, каждое отдельной функцией;
- `engine.ts` — `checkPlan`, `dayLoad`, `loadRange`, `findWindows`, `teamConflicts`;
- `fromDb.ts` — перевод строк базы в типы движка, коды правил R01… ↔ движок, `changeFromDb` для `part_changes`;
- `trim.ts` — советы «где освободить дни»;
- `change.ts` — изменение согласованного отпуска: `checkChange`, `applyChange`, `withOpenChanges` (для загрузки
  группы, пока заявка открыта: заняты и старые, и новые даты), `extendForSickness`, `recallFromVacation`;
- `sample.ts` — 18 вымышленных сотрудников, планы на 2027 год и одно исключение HR;
- `index.ts` — публичный API.

## Чего движок не делает

Не считает отпускные и сроки их выплаты (ст. 175–176), не ведёт счётчики ст. 189/190 за год и
сдвиг рабочего года по дням без сохранения (`workingYear` принимает готовый сдвиг), не проверяет
выполнимость групп на год (ст. 170 ч. 1) и уведомление за 15 дней (ст. 169) — это следующие кандидаты.
